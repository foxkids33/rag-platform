# Персональные подключения пользователей к Confluence

Статус: архитектурный план и анализ существующего кода, **не внедрённая
функция персонального входа**. Старый общий коннектор не следует открывать
обычным пользователям: он работает с правами настроившего его оператора.

## Требуемое поведение

Каждый пользователь RAG самостоятельно подключает собственную учётную
запись Confluence. Поиск/выбор/импорт получают ровно те страницы, которые
Confluence разрешает предоставленному пользователем credential. Его
импортированные документы, результаты и история остаются в его пространствах.
Сервер выполняет сетевые запросы вместо ноутбука, но не подставляет при
этом личный PAT администратора RAG или общий credential другого пользователя.

Вход в RAG не является входом в Confluence. Совпадение логина или наличие
локальной RAG-сессии не доказывает личность пользователя в Confluence.

## Подтверждённый сетевой блокер

При read-only проверке сервера 192.0.2.122 DNS вернул
`192.0.2.104`, а обычный маршрут выбрал Docker-сеть
`192.0.2.0/16`, принадлежащую другому проекту (`totum-production_database`).
Сеть этого проекта не изменялась и не удалялась.

Проверка маршрута с принудительным выходом через корпоративный `br0`
показала шлюз `192.0.2.254`, но HTTPS-запрос, привязанный к `br0`,
также завершился timeout. Поэтому добавление host route само по себе
пока не доказано как рабочее решение. Нужен разрешённый сетевой путь
от сервера до `192.0.2.104:443` и проверка ACL/firewall/маршрутизации
со стороны корпоративной сети. Никаких личных токенов для этой проверки
не передавалось. Таблица маршрутов хоста не менялась.

Пока TCP/HTTPS недоступен, ни общий service-account connector, ни личный
PAT, ни OAuth не сделают серверный импорт работоспособным.

### Повторная проверка с временным host route

Проверены `rp_filter`: all=0, br0=2 (loose), то есть предположение о
strict reverse-path filtering не подтвердилось. Для исключения обычного
выбора Docker route был временно добавлен только маршрут
`192.0.2.104/32 via 192.0.2.254 dev br0 metric 427`.
`ip route get` подтвердил нужный корпоративный интерфейс и source
`192.0.2.122`, но HTTPS REST-запрос с проверкой сертификата и фиксированным
целевым IP снова не установил TCP-соединение за 7 секунд. Авторизация не
отправлялась. Маршрут удалён в finally, первоначальный route восстановлен.

Это не позволяет определить конкретное upstream-устройство по одному
таймауту, но означает, что одной замены Docker route пока недостаточно.
Нужна проверка маршрута, firewall/ACL и обратного пути сетевым администратором.

Текст сетевой заявки: «Нужен HTTPS-доступ с сервера 192.0.2.122 к
confluence.example.invalid (192.0.2.104), TCP443. Текущая Docker-сеть другого
проекта 192.0.2.0/16 перекрывает цель. С временным более точным маршрутом
через штатный шлюз 192.0.2.254 и интерфейс br0 HTTPS также получает
connect timeout. Просим согласовать корректный маршрут, ACL и обратный путь;
чужие Docker-сети не перенумеровывались».

## Предпочтительный постоянный путь: delegated OAuth/SSO

Нужна подтверждённая поддержка используемой редакцией/версией Confluence
и регистрация приложения корпоративным администратором:

- approved client ID, redirect URI на HTTPS RAG и разрешённые scopes;
- параметры issuer/authorization/token endpoints и согласованный grant;
- привязка callback к вошедшему RAG-пользователю через state; PKCE при
  поддерживаемом authorization-code flow; запрет произвольного redirect;
- серверная проверка upstream identity, не значение subject из браузера;
- encrypted-at-rest token storage или корпоративный vault/KMS, привязка к
  tenant + RAG subject + фиксированному Confluence origin;
- expiry/refresh/revocation/disconnect и отсутствие токенов в логах,
  localStorage, обычных очередях, документах или истории чатов.

Не изобретать OAuth endpoints по аналогии с Cloud: для корпоративного
Confluence Data Center необходимо проверить реальную конфигурацию и
возможности администратора. Без такой регистрации нельзя обещать кнопку
«Войти через Confluence», которая действительно реализует delegated login.

## Минимальный пилот: PAT пользователя только на время запроса

Это не SSO и не постоянное «подключение». Пользователь сам создаёт PAT
на разрешённой корпоративной стороне и вводит его в HTTPS-форму RAG для
проверки/импорта. RAG не сохраняет PAT после запроса. Это позволяет убрать
ноутбучный коннектор без немедленного внедрения vault и OAuth refresh.

Уже существующие компоненты:

- `ConfluenceCredentials` принимает обязательный `SecretStr token`;
- `POST /api/v1/integrations/confluence/check` создаёт отдельный
  `ConfluenceClient(token=...)` и закрывает его в finally;
- `POST /api/v1/workspaces/{workspace_id}/imports/confluence` принимает
  персональные credentials, проверяет owner пространства до upstream-запроса
  и читает страницы этим отдельным клиентом;
- в очереди ingestion находятся только document ID и служебные поля;
  исходный PAT не добавляется в снимок страницы/MinIO/чат;
- base URL фиксируется сервером; pagination не может уйти на другой origin.

Что **ещё требуется**, прежде чем разрешать этот путь обычным пользователям:

1. Устранить сетевой конфликт на сервере и проверить HTTPS Confluence с
   верификацией сертификата. DNS или ping для этого недостаточны.
2. Включить personal import capability без server-level PAT. Оставить
   fixed Confluence URL и verified TLS; не принимать произвольный URL клиента.
3. Для personal-request router использовать обычную RAG-аутентификацию,
   а не admin-only wrapper. При этом **не снимать admin-only** с общего
   connector/direct-server-account router и его заданий.
4. Добавить персональный список пространств/дерево страниц, если нужен
   выбор в UI, с обязательными credentials на каждом запросе. Не использовать
   общий connector для discovery пользователя.
5. В UI показать персональную форму PAT и явно обозначить отсутствие
   сохранения токена. Хранить его только в памяти формы, очищать после
   операции/выхода/смены пользователя; не переносить cookie корпоративного
   браузера и не запрашивать корпоративный пароль.
6. Перед импортом применить пользовательские квоты. Текущий `_import_page`
   ещё не использует новые `size_bytes` и upload quotas: открытие маршрута
   без этого обойдёт лимиты диска через Confluence import. Для обновлений
   учитывать заменяемый размер, для unchanged skip не расходовать квоту.
7. Ограничить число страниц, параллелизм, upstream timeouts и суммарное
   время запроса. Не сохранять PAT в обычный job payload ради async retry.
8. Реальные проверки A/B: токен A не используется для B, чужие workspace/
   page ID не обходят RAG owner checks, 401/403 upstream не приводят к
   fallback на токен оператора, secrets не отражаются в ошибках/логах.

Полезная гарантия этого первого пилота: после запроса нет сохранённого
upstream credential. Ограничение: фоновая синхронизация без нового ввода PAT
невозможна. Для постоянной синхронизации понадобится delegated token или
явно сохраняемый credential с encryption/vault и owner-bound очередью.

## Права и актуальность после импорта

Confluence проверяет права при чтении страницы. Это не автоматически
отзывает уже сохранённый снимок, если затем изменились ACL или PAT.
Политика должна явно определить:

- является ли импорт личной копией с сохранёнными URL/version/synced_at;
- нужна ли свежая проверка прав перед каждым поиском/ответом;
- как выключать из поиска удалённую/закрытую страницу и её старые версии;
- как очищать цитаты, историю, кэш и файлы при disconnect или отзыве доступа;
- что может видеть администратор RAG и какие действия попадают в аудит.

Нельзя обозначать такой пилот как «полное зеркалирование Confluence ACL»,
пока эти случаи не реализованы и не проверены. Тем более нельзя сначала
импортировать общий широкий корпус личным PAT оператора и открыть его всем
зарегистрированным пользователям.

## Порядок внедрения

Сначала server-side network и персональный request-scoped PAT import в
собственное пространство. После проверки — управляемый disconnect и
актуальность прав. Далее — согласованное delegated OAuth/SSO и encrypted
per-user connection storage для фона. Общая техническая учётка остаётся
отдельным, явно администрируемым вариантом для корпоративной базы знаний,
а не заменой персонального входа.
