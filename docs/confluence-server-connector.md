# Постоянный Confluence Connector на сервере

Этот профиль описывает общую техническую учётную запись для администратора. Сотрудники могут подключить свою учётную запись по [инструкции «Мой Confluence»](personal-confluence-connections.md).

Профиль подготовлен отдельно от RAG и ничего не запускает автоматически.
Он не копирует личный PAT, не меняет маршруты хоста и не пересоздаёт чужие
Docker-сети. Перенос допускается после проверки сети и получения технической
учётной записи Confluence.

## Две независимые задачи

1. Убрать зависимость от ноутбука: запустить outbound connector на сервере.
2. Убрать зависимость от личной учётки: выдать отдельной технической учётной
   записи read-only доступ только к утверждённым пространствам Confluence.

Перенос с личным PAT решает только первый пункт. Ни этот профиль, ни RAG
не создают корпоративные учётные записи и не меняют Confluence ACL.

## Почему сейчас сервер не читает Confluence

`confluence.example.invalid` разрешается в `192.0.2.104`, а маршрут к этому IP
выбирает Docker-мост с подсетью `192.0.2.0/16`. Разрешение DNS не означает
наличие правильного маршрута. Это конфликт адресных пространств.

До переноса нужно определить владельца конфликтующей Docker-сети и правильный
корпоративный шлюз. Не удалять мост и не выполнять `docker network prune`:
сеть может принадлежать другому проекту. Точечный маршрут или изменение Docker
address pools требует проверки существующих маршрутов и влияния на соседей.
Отсутствие ответа на ping само по себе не доказывает недоступность HTTPS.

Фактическая проверка `curl --interface br0` к HTTPS Confluence тоже дала
timeout, хотя `ip route get ... oif br0` указал шлюз `192.0.2.254`.
То есть одного обхода Docker route оказалось недостаточно. Доступ до
`192.0.2.104:443` должен быть согласован и подтверждён сетевой стороной;
этот профиль не объявляется работоспособным на сервере до такой проверки.

05.11.2026 дополнительно проверен `internal-service.example.invalid`: VPN-авторизация успешна,
но HTTPS Confluence через изолированный туннель также даёт timeout. Адрес
Confluence не входит в 24 выданных split include маршрута; подробности и
необходимые сетевые проверки — в [отчёте VPN-пробы](confluence-vpn-diagnostics-2026-11-05.md).

## Что подготовить

- Техническую учётную запись, её PAT и минимальный список space keys.
- Маршрут и HTTPS до настоящего Confluence, включая проверку сертификата.
- Отдельную машинную регистрацию server connector в RAG. Не переносить
  credential работающего ноутбука и не использовать один credential параллельно.
- Приватный host state directory UID/GID `10001:10001`, mode `0700`.
- `state/credential.json` от новой регистрации: owner `10001:10001`, mode `0600`.
- Файл PAT технической учётки: owner `10001:10001`, mode `0400` или `0600`.
- Публичный CA/certificate для HTTPS RAG и CA bundle для Confluence.

Секреты передавать защищённым способом, не через chat, argv или env-файл.
Права `0600` не являются шифрованием и не защищают от root/владельца хоста;
для постоянной эксплуатации предпочтителен корпоративный secrets manager.

Первичную регистрацию выполняет администратор RAG через штатный enrollment API,
а полученный одноразовый token обменивается на отдельный machine credential.
В permanent service одноразовый token не передаётся: он запускается только с
готовым защищённым `credential.json`. Роли пользователей и machine credential
не взаимозаменяемы. При другой RAG URL нужна новая отдельная привязка.

## Профиль запуска

Файлы:

- `deploy/docker-compose.confluence-server.yml`;
- `deploy/confluence-server.env.example`;
- `scripts/deploy/server_connector_preflight.py`.

Создать собственную копию env-примера и указать реальные private-file пути.
Сам env-файл содержит только настройки и пути, без секретов. Не запускать
на хосте, пока техническая учётная запись и её доступ не согласованы.

```bash
cd /home/intern/ZMostovoy/rag-platform

# Сначала проверить итоговую конфигурацию; она не содержит PAT/пароля.
sudo docker compose --env-file deploy/confluence-server.env \
  -f deploy/docker-compose.confluence-server.yml config --quiet

# Сборка и запуск только отдельного сервиса connector.
sudo docker compose --env-file deploy/confluence-server.env \
  -f deploy/docker-compose.confluence-server.yml build connector
sudo docker compose --env-file deploy/confluence-server.env \
  -f deploy/docker-compose.confluence-server.yml up -d connector

sudo docker compose --env-file deploy/confluence-server.env \
  -f deploy/docker-compose.confluence-server.yml logs --tail 60 connector

# Штатный end-to-end check без получения заданий или импорта.
sudo docker compose --env-file deploy/confluence-server.env \
  -f deploy/docker-compose.confluence-server.yml run --rm --no-deps connector --check
```

Профиль использует уже существующую сеть `rag-zmostovoy_default`, а не создаёт
новый bridge/подсеть. Контейнер работает UID10001, без capabilities, с read-only
root filesystem и read-only credential directory. Входящих портов нет.
Память, CPU, временные файлы и логи ограничены. Перезапуск — `unless-stopped`.
Preflight не допускает inline PAT, cookie-mode, wildcard/personal spaces,
отключённый TLS и world-readable credential files.

В текущем Dockerfile базовый образ/установка зависимостей ещё не фиксированы
по digest/lock-файлу. Перед постоянной эксплуатацией нужен воспроизводимый
build; этот подготовленный профиль не объявляется уже развёрнутым или
полностью проверенным production-компонентом.

Важно: root filesystem контейнера read-only не означает, что сервер стал
полноценным secrets vault. Root хоста по-прежнему доверенный оператор.

## Проверка и отключение ноутбука

1. Подтвердить HTTPS RAG и source Confluence, не только process alive.
2. Войти администратором RAG: новый server connector должен быть online.
3. Выполнить `LIST_SPACES` и чтение согласованной тестовой страницы; проверить
   server-side allowlist. Не импортировать всё пространство автоматически.
4. Проверить один согласованный импорт и `READY`, при необходимости убедиться
   в идемпотентности повторного импорта.
5. Только после успешной проверки остановить ноутбучный сервис и отозвать
   именно его machine credential в RAG.
6. Отозвать личный Confluence PAT у источника, если он больше нигде не нужен.
   Не отзывать чужие коннекторы или корпоративные токены других приложений.

До шага5 ноутбук остаётся резервом. Нельзя сначала выключить единственный
рабочий источник, а потом выяснять, что техническая учётка не готова.

## Границы доступа

В текущем password-mode новый пользователь RAG видит свои пространства,
документы, KB и чаты. Общая Confluence-интеграция доступна администратору.
Это не автоматическое зеркалирование Confluence ACL на каждого пользователя.
Уже импортированные личным PAT снимки сами собой не становятся публичными,
но техническая учётка не меняет ретроспективно их права и происхождение.

Если требуется выдавать корпоративный корпус обычным пользователям, сначала
нужны явные grants/memberships либо проверка Confluence ACL per user, включая
поиск, контекст, цитаты, историю и кэш; одной видимости sidebar недостаточно.

## Следующие улучшения пилота

1. Независимый server connector и service account; контроль сети и TLS.
2. Мониторинг диска, readiness источника отдельно от heartbeat, alerts/retry.
3. Плановые обновления документов и управляемая публикация версий KB.
4. Явные права на общие KB и аудит импорта/доступа, если нужны shared corpora.
5. Воспроизводимый corpus eval; reranker включать только после сравнения
   одинаковых запросов/корпуса с retrieval quality, полнотой ответа и latency.
