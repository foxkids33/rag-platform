# Разработка и выпуск на сервер

## Работа с изменениями

Для разработчика рабочая копия — обычный клон GitHub. На сервере используйте отдельный клон рядом с каталогом работающего приложения. Автор пушит со своей учётной записью GitHub с правом записи. Для общего серверного пользователя используйте отдельный клон и собственную SSH-сессию с доступом к GitHub. У сервиса доставки достаточно доступа на чтение.

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/confluence-import
# Внесите изменение и проверьте его
git add -p
git commit -m "Уточнить импорт страниц Confluence"
git push -u origin HEAD
```

Откройте pull request из своей ветки в `main`. CI запускает тесты API с PostgreSQL/pgvector, проверяет миграции, воркер, коннектор, embedding/reranker, сборку web, клиентскую авторизацию и тесты эксплуатации. После слияния и успешных проверок `main` GitHub Actions перемещает ветку `deploy/production` на испытанный коммит. [Workflow](../.github/workflows/ci.yml)

## Что происходит на стенде

Системный таймер раз в две минуты проверяет `deploy/production` по исходящему HTTPS. Сервис держит отдельную копию Git с правами root. Он проверяет, что версия принадлежит истории `main`, и собирает изменившиеся образы. Для API и воркера используются production Dockerfile, для web — существующая HTTPS-конфигурация площадки и свежая сборка React. У коннектора своя служба; её можно перезапускать при активном туннеле Cisco. Изменения только документации обновляют номер версии без перезапуска приложений.

До переключения сервис сохраняет прежние идентификаторы образов. При изменении версии схемы он делает `pg_dump` перед стартом API с Alembic. После переключения он проверяет версию запущенных образов, ответ HTTPS health и HTTP 401 для анонимного запроса к рабочим областям. При ошибке он возвращает предыдущие образы. Миграции для автоматического выпуска должны быть совместимы с предыдущей версией приложения. Восстановление БД из резервной копии остаётся отдельным решением оператора. Выпуск API также перезапускает web, чтобы nginx заново разрешил адрес API.

```bash
systemctl list-timers rag-delivery.timer
sudo journalctl -u rag-delivery.service -n 50 --no-pager
sudo cat /var/lib/rag-delivery/applied.json
```

Значение `applied.json` — SHA, который сервер успешно применил. После неудачного переключения `failed.json` содержит отклонённый SHA. Таймер продолжает принимать следующие зелёные версии. Для повтора той же версии после исправления причины оператор удаляет `failed.json` и запускает `sudo systemctl start rag-delivery.service`. Обычный откат изменений исходного кода — `git revert` через pull request.

## Установка агента на существующий защищённый стенд

Установите `deploy/delivery/poll.py` в `/usr/local/libexec/rag-delivery/`, а файлы службы и таймера — в `/etc/systemd/system/`. Создайте `/etc/rag-delivery` с режимом 0700. Скопируйте действующие базовый Compose и защищённый override в `base.yml` и `secure.json` в этом каталоге. Заполните `site.env` по [шаблону](../deploy/delivery/site.env.example), укажите действующий корень проекта, имя Compose-проекта, внешний HTTPS URL и доверенный CA. Закройте доступ к файлам другим пользователям. При изменении топологии или TLS-конфигурации оператор обновляет файлы площадки. Агент использует действующий `.env.demo`, хранилища и постоянные Docker volumes. Служба Cisco и параметры шлюза обслуживаются отдельно от выкладок приложения.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now rag-delivery.timer
sudo systemctl start rag-delivery.service
```
