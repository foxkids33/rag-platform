# Повторное использование RAG другими командами

Дата проверки: 21 октября 2026 года. Основание — исходники, определения тестов и сохранённые агрегаты оценки. Работающие серверы, реальные учётные данные, корпоративные тексты, ответы отдельных тестовых случаев и дампы не проверялись. Реальные `.env` не читались; приложения, миграции и сетевые запросы в рамках этого обзора не запускались. Наличие теста ниже означает наличие проверки в репозитории, а не новый успешный прогон.

## Вывод и область применения

Проект уже представляет полезную основу внутреннего поиска и ответов по технической документации: импорт Confluence, загрузка документов, гибридный поиск, ответы с источниками, сохранение диалогов и управляемые версии общих баз знаний. Его можно переносить в другую команду с собственным разрешённым корпусом и отдельно проверенными моделями. Настройки и корпус конкретного пилота не должны становиться частью нового продукта по умолчанию.

Наиболее подходящие пользователи — инженерная поддержка, эксплуатация, архитекторы и команды, которым нужно искать процедуры, точные идентификаторы и примеры команд в общей документации. Результат следует использовать как помощь специалисту с возможностью открыть источник. Приложение не выполняет найденные команды и не подтверждает их применимость к конкретному рабочему стенду.

Пока не подтверждены следующие обещания: сохранение индивидуальных прав всех пользователей Confluence; полное понимание диаграмм и вложений; непрерывно актуальное зеркало без отдельной синхронизации; гарантированная точность на произвольной базе другой команды; промышленный SLA под параллельной нагрузкой.

## Схема переносимого развёртывания

Для обычной команды достаточно прямого соединения API с Confluence и прямого соединения с сервисами моделей. Основной контур: web → API; API → Confluence и LLM; API/worker → embedding; API/worker → PostgreSQL и объектное хранилище. Worker обрабатывает принятые задания. Коннектор добавляется, когда API не может обратиться к Confluence из своей сети.

Это несколько контейнеров и внешние зависимости, а не один самодостаточный образ. Для простоты нужен один изолированный Compose-проект с собственными volumes и явными параметрами. Перенос не должен зависеть от старого имени проекта, существующего workspace, снимка конкретного space или сохранённого credential коннектора. Текущий [server Compose](../deploy/docker-compose.server.yml) содержит привязки существующего пилота; новый clean-профиль и переключатель режимов должны проходить самостоятельную проверку. Этот обзор не удостоверяет их развёртывание.

Контракты моделей отличаются:

- LLM: OpenAI-совместимый `POST /v1/chat/completions`, сообщения, `model`, `temperature`, `max_tokens`; поток — SSE. API key предусмотрен. Специфичный `chat_template_kwargs.enable_thinking` отправляется только при соответствующей настройке. Основание: [llm.py](../apps/api/app/services/llm.py).
- Embedding: `POST /embed`, тело с `inputs`, `normalize`, `truncate`, `input_type=query|passage`; ответ — массив векторов фиксированной размерности. Это не универсальный OpenAI `/v1/embeddings`. Контракт должны одинаково выполнять [API](../apps/api/app/services/embeddings.py) и [worker](../apps/worker/app/embeddings.py). Отдельного bearer-параметра embedding-клиента в этих файлах нет.
- Reranker: необязательный `/rerank` с `query` и `documents`, ответ содержит `scores`. Нужен совместимый сервис, а не только URL произвольного inference endpoint: [reranker.py](../apps/api/app/services/reranker.py).

Размерность, embedding-модель и обработка query/passage должны совпадать во всём контуре. Смена embedding-модели требует переиндексации; одинаковая размерность не означает одинаковое пространство векторов. [Инициализатор схемы](../apps/api/app/operations/initialize_embedding_schema.py) запрещает менять размерность непустой таблицы и по умолчанию требует отдельного разрешения записи. Это полезная защита, а не автоматическая миграция корпуса.

## Приоритетные условия допуска

**1. Определить границу доступа до общего использования.** В [моделях](../apps/api/app/db/models.py) есть tenant, владелец workspace и источник документа; ACL страницы/группы Confluence и его версия не представлены. Allowlist пространств ограничивает область импорта, но не переносит ограничения отдельных страниц. Для первой команды допустим явно согласованный корпус, который разрешён всем пользователям общей базы. Для разных групп с разными правами нужен механизм ACL либо отдельные разрешённые корпуса и доступы. OIDC должен быть включён для защищённого совместного использования; локальный режим подходит только изолированному пилоту. Frontend OIDC уже существует, хотя часть старой документации описывает его как будущую работу.

**2. Зафиксировать обновление и отзыв информации.** [Прямой импорт](../apps/api/app/api/routes/confluence.py) повторно использует документ, сравнивает hash, сохраняет `external_version` и `synced_at`; повторный импорт не должен создавать копии. Сам импорт списка страниц не доказывает автоматического отслеживания всех удалений и потери доступа. [sync.mjs](../scripts/confluence/sync.mjs) отдельно обходит источник и отключает отслеживаемые workspace-документы при подтверждённых 403/404 или уходе из space; сетевой сбой не трактуется как удаление. Это отдельный операторский процесс, не гарантия непрерывной синхронизации UI или опубликованной базы. Нужны владелец, периодичность, журнал, порог устаревания и проверяемая процедура отзыва.

**3. Различать удаление источника и удаление его следов.** Удаление документа использует транзакционную очередь очистки объектов; chunks связаны с документом каскадно. Однако [сохранение ответа](../apps/api/app/api/routes/answer.py), `_persist_exchange` и `_assistant_metadata`, записывает текст и снимок источников в `ChatMessage.metadata`. Чтение [истории](../apps/api/app/api/routes/conversations.py) возвращает сохранённые сообщения. Удаление документа само по себе не редактирует старые ответы и цитаты. Для требований отзыва доступа/удаления нужны отдельная политика истории, retention и резервных копий и её тесты.

**4. Проверить готовность моделей и зависимостей.** [API health](../apps/api/app/api/routes/health.py) сообщает жизнеспособность процесса, не проверяя БД, worker, Confluence или inference. У embedding/reranker есть собственные readiness-маршруты. Для эксплуатации нужны отдельные проверки реального поиска, генерации и индексации, контроль очереди и возраста зависших заданий, ошибок/timeout, свежести корпуса и задержки ответа. [Backup-инструкция](deployment.md) существует, но восстановление, RPO/RTO и нагрузочные пределы в этом обзоре не проверялись.

**5. Проверить контент и качество именно новой команды.** Вложения и изображения не следует объявлять прочитанными, пока они не попали в подтверждённый pipeline. Сохранение команды без искажения не подтверждает её актуальность и безопасность для другой версии продукта. Проверка цитат по номерам и code-integrity guard полезны, но не заменяют проверки применимости и фактов.

## Проверяемые критерии передачи другой команде

1. **Чистый запуск:** пустые volumes, уникальное имя Compose-проекта, отсутствие старых workspace/credentials/корпуса; создаются БД и bucket, проходит одна тестовая загрузка, поиск, ответ и перезапуск с сохранением данных. Никаких чужих production volumes в команде запуска.
2. **Прямой режим:** с доступной сетью API напрямую читает разрешённый Confluence; модели доступны без локального коннектора. Проверить Cloud/Data Center, применяемую схему авторизации и CA. Режим connector проверить отдельно только для разделённых сетей.
3. **Доступ:** без токена — 401 при включённом OIDC; чужой tenant/workspace — 404; обычный пользователь не меняет общую базу. Проверить прямой API, поиск, выдачу файлов и историю. Для первой версии документировать единые права на общий корпус; не заявлять page ACL без реализации и отрицательных тестов.
4. **Свежесть и удаление:** добавить страницу, изменить версию, повторно импортировать без копии, закрыть доступ/удалить страницу и подтвердить исключение из поиска. Сбой 5xx не должен массово удалять корпус. Отдельно проверить историю, snapshots и backup в рамках утверждённой политики хранения.
5. **Совместимость моделей:** фиксировать model ID, ревизию, embedding dimension, context/output limits и версии chunker; API/worker используют одну embedding-конфигурацию. Проверить streaming, timeout, неверную размерность и отказ inference. Не считать любой OpenAI endpoint совместимым со всеми тремя контрактами.
6. **Оценка пользы:** собрать вопросы новой команды и эталонные версии статей; разделить dev и независимый holdout по статьям/сценариям до настройки. Измерять Recall@k/MRR, полноту и точность фактов, корректные отказы, покрытие источниками, критичные команды и ошибки. Публиковать числитель/знаменатель, конфигурацию и ограничения. Пороги согласовать до просмотра holdout; существующие числа не переносить автоматически.
7. **Эксплуатация:** измерить p50/p95 и долю timeout при заявленной конкурентности и длине контекста; проверить восстановление очереди после сбоя worker и отказа Redis, очистку объектов, backup/restore и откат версии приложения без удаления volumes. Назначить ответственных за обновления образов, моделей и корпуса.

После этих проверок карточка решения в каталоге может честно обещать «развёртываемый RAG для согласованной базы команды». Обещание универсального защищённого поиска по всему Confluence требует отдельного подтверждения ACL, свежести и качества.
