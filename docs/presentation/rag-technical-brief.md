# RAG Platform: техническая записка для архитектурного комитета

Основание: локальный код, конфигурация демонстрационного развёртывания и
зафиксированные проверки 8 октября 2026 года. Это описание устройства и
подтверждённого объёма демонстрации, а не проверка текущей доступности стенда.

## Задача и границы системы

Платформа помогает техническому писателю и инженеру находить сведения в
документации и получать ответ с проверяемым происхождением: исходная страница,
её версия и использованный фрагмент. Это не обучение модели на корпоративных
статьях: документы индексируются отдельно, а генератор получает отобранный
контекст конкретного вопроса. Документация также не заменяет телеметрию:
утверждение о текущем состоянии оборудования требует другого источника.

Демонстрационный Compose содержит ровно семь сервисов:

- `web` — React-интерфейс и Nginx, входная точка пользователя;
- `api` — FastAPI: workspace, базы знаний, поиск, ответы и задания импорта;
- `worker` — отдельный процесс разбора документов и индексации;
- `postgres` — PostgreSQL 16 с pgvector, документы, чаты, версии, задания,
  полнотекстовый индекс и векторы;
- `redis` — уведомления, ускоряющие получение фоновых заданий;
- `minio` — объектное хранилище исходных документов и снимков страниц;
- `embedding` — GPU-сервис BGE-M3 для построения поисковых векторов.

Генерация использует уже существующий общий vLLM с
`Qwen/Qwen3.8-27B-FP8`. Он не является восьмым контейнером этого Compose и
не управляется жизненным циклом RAG. Коннектор Confluence работает на
компьютере пользователя, тоже вне серверного Compose.

Такое разделение позволяет обновлять UI, API или парсер независимо;
тяжёлая индексация не выполняется внутри HTTP-запроса поиска. GPU-модель
embedding имеет собственные ограничения параллелизма и readiness-проверку.
Это изоляция компонентов, не заявление о высокой доступности: отказ общей
GPU, PostgreSQL или внешнего LLM остаётся существенной зависимостью.

## Как документ становится поисковым источником

Коннектор сам устанавливает исходящие соединения с RAG и Confluence,
получает ограниченный набор заданий и возвращает результаты. Это не
универсальный удалённый HTTP-прокси. PAT Confluence остаётся на компьютере
пользователя; сервер получает страницы, а не этот секрет. Отдельный credential
коннектора привязан к конкретному RAG-адресу. Выбор всех доступных пространств
означает перечисление реально видимых пространств настроенной учётной записи,
а не обход прав Confluence.

Страница поступает как JSON-конверт со storage XHTML, идентификатором,
версией и исходным URL. MinIO хранит исходные байты, PostgreSQL — их SHA-256,
метаданные и состояние обработки. Это разделяет большие объекты и
транзакционные связи; исходник можно повторно разобрать после изменения
парсера, не считая embedding единственной копией знания.

API сохраняет задание в PostgreSQL. Redis отправляет best-effort уведомление:
его потеря не должна терять задание. Worker выбирает строки с
`FOR UPDATE SKIP LOCKED`, использует lease и heartbeat, возвращает зависшие
задания в очередь либо завершает их ошибкой после ограниченных попыток.
Готовность документа и его chunks записываются транзакционно.

Парсер сохраняет заголовки, таблицы и целые блоки кода; код не исполняется.
Небольшие дочерние chunks нужны для поиска, а родительский раздел — для
расширения контекста ответа. Крупный блок кода не режется на произвольные
куски, но embedding ограничен длиной входа: сохранение полного текста не
означает, что каждый его токен представлен поисковым вектором.

Confluence использует структурное группирование блоков по breadcrumb, а не
sliding overlap. Лимит child по умолчанию — 2200 символов, parent — 12 000;
код может превышать лимит как oversized atomic block. Overlap 300 символов
относится к plain-text splitter. В ответе сначала выбираются leaf-фрагменты,
затем они расширяются до parent в оставшемся бюджете. Непоместившееся продолжение
помечается явно; полного покрытия всех команд разных разделов это не гарантирует.

## Поиск и контролируемая генерация

`BAAI/bge-m3` строит нормализованные dense-векторы размерности 1024,
инференс выполняется в FP16. В этом сервисе отключены sparse и ColBERT
выходы BGE-M3. Qwen выполняет другую задачу — генерирует текст ответа;
она не является текущей embedding-моделью.

Dense-поиск использует cosine distance pgvector. Лексический канал —
полнотекстовый поиск PostgreSQL с конфигурациями `russian` и `simple`.
Hybrid объединяет ранги через Reciprocal Rank Fusion, `k = 60`; отдельный
канал точных идентификаторов получает повышенный вес. Число RRF — оценка
ранжирования, не вероятность правильности. Чистый режим `dense` не включает
канал точных идентификаторов. Cross-encoder предусмотрен кодом, но на
демонстрационном стенде reranker выключен; графовый поиск также не включён.

Hybrid-вклад: `1/(60+dense_rank) + 1/(60+lexical_rank)
+ 3×exact_score/(60+exact_rank)`; `exact_score` — доля найденных точных
идентификаторов вопроса. У предусмотренного reranker веса рангов 0,7/0,3
для rerank/retrieval и дополнительный штраф boilerplate; exact evidence
имеет приоритет перед выигрышем только по модели. Это эвристики ранжирования,
не проценты уверенности. В demo эти reranker-коэффициенты не участвуют в поиске.

Перед генерацией проверяются доступ к workspace, область источников,
готовность документов, разнообразие фрагментов и бюджет контекста.
Для распознанных точных идентификаторов действует anchor guard: они должны
присутствовать даже в окончательно выбранных фрагментах, иначе система
сообщает о недостатке подтверждений. Это целевой предохранитель, не
универсальная проверка всех возможных утверждений.

Ответ проверяется на допустимые номера ссылок. Для fenced-кода определяется
дословное совпадение с полным закрытым блоком из контекста, действительно
переданного модели, и возвращаются SHA-256 и свидетели: URL, page ID, версия.
Допустима нормализация CRLF и разделителя перед закрывающим fence; параметры,
пробелы и порядок строк не «исправляются». При явном запросе дословного кода
неподтверждённый блок удерживается контрактом ответа. Генерация буферизуется
до проверки, чтобы непроверенный текст нельзя было показать и затем отозвать.
Совпадение блока не доказывает безопасность команды, полноту процедуры или
применимость к конкретной системе; исходную статью всё равно нужно открыть.

## Версии, конфиденциальность и измеримость

Workspace и активная версия KB задают область SQL-поиска. Курация создаёт
отдельные объекты выбранных страниц с сохранением происхождения и запускает
повторную индексацию, а не копирует готовые vectors. Опубликованное содержимое
версии неизменяемо через обычные операции редактирования; обновление живого
workspace не меняет его автоматически. Новая публикация переключает активную
версию. Это воспроизводимость корпуса, не зеркало индивидуальных Confluence
ACL: пилот работает без пользовательской авторизации. Для многопользовательской
эксплуатации необходимы авторизация и проверка прав на импортированные данные.

Источники, индексы и генерация расположены внутри корпоративной сети;
OpenAI-compatible означает протокол, а не отправку документов в OpenAI/SaaS.
Docling в demo-сборке отключён. Изображения и нераскрытые визуальные макросы
дают явные placeholders и предупреждения; OCR/vision и понимание схем не
заявляются готовыми.

KV-cache генератора хранит тензоры ключей/значений attention: prefill
обрабатывает вход, decode добавляет выходные токены, используя предыдущие K/V.
Опциональный [prefix caching vLLM](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)
повторно использует вычисления точного общего префикса при prefill; сам decode
это не ускоряет. Это не база знаний, pgvector, Redis или кэш BGE. FP8 в
имени Qwen описывает веса, не доказывает тип KV-cache. Настройки общего
сервера, включение prefix caching и доля попаданий здесь не подтверждены.

Для нашего RAG это направление оптимизации: `_messages` уже
ставит контекст перед вопросом, но history находится перед ним, а поиск
меняет набор и порядок excerpts. Одинаковая KB поэтому не гарантирует cache
hit. Стабильный версионированный контекст может быть пригоден для reuse,
но это не реализованная фича приложения и не подтверждённое ускорение.
Хеш одинакового контекста не заменяет доказательство cache hit.
По решению автора выступления новые замеры и тесты не проводятся; общий
cache и конфигурацию inference ради показа не изменяем.

Для диагностики нужно разделять импорт, поиск, построение контекста, ожидание
общего LLM, генерацию и проверки ответа. SSE-метаданные содержат режим поиска,
использованные источники и признаки проверок, но время до первого видимого
текста из-за буферизации не равно чистому TTFT модели. Проверки 8 октября:
309 текущих страниц выбранного пространства в `READY`, три активные KB по
четыре страницы, девять подготовленных ответов. Expected-page Hit@5 равен
8/8 для dense, lexical и hybrid на восьми отрепетированных положительных
вопросах в маленьких KB. Это приёмка демонстрационных сценариев, не независимый
benchmark, общая точность, доказательство превосходства hybrid или SLA.
