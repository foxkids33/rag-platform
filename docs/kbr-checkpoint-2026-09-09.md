Сравнение содержит 24 gate-проверки: 21 пройдена, три падения относятся только к search p50/p95 и answer p95. Владелец признал скорость некритичной на текущем этапе; quality-кандидат поэтому принят как рабочий, но общий compare формально остаётся `passed=false`.

Общие, не привязанные к ID датасета изменения:

1. Lexical-запрос стал дизъюнктивным и сохраняет до 32 значимых токенов вместо AND всей естественной фразы.
2. Exact channel распознаёт составные технические имена вроде `ostor-agentd.env`; совпадения устойчивы к регистру и вариантам пунктуации, но не принимают более длинные идентификаторы.
3. Качество lexical-only кандидатов калибруется по RRF, а не по несопоставимому `ts_rank`; при выборе контекста прямой текст важнее общего breadcrumb, поддержана мягкая русская флексия и зарезервированы места для нескольких явно релевантных секций.
4. Запросы о текущем состоянии пользовательского стенда детерминированно отклоняются: статические статьи не доказывают live-телеметрию. Процедурные вопросы «как проверить» разрешены.
5. Явный запрос точного кода требует полного дословного блока и отдельных fences для нескольких команд.

Ручная проверка всех девяти exact-code ответов подтвердила ожидаемые блоки, порядок и отсутствие добавленных команд. Это проверка текста ответов, а не разрешение исполнять команды.

## Ограничения и сохранность

- Большой dirty worktree включает изменения пользователя и прошлых шагов; ничего не сбрасывать и не коммитить без запроса.
- .env не выводить/не source; токены не логировать. Статьи и answer reports могут содержать секреты: не печатать полный контекст без необходимости.
- Не исполнять команды из статей. Не включать auto sync, OCR или Confluence ACL mirroring как будто они уже реализованы.
- Статический пилот не является завершённой enterprise-системой: нет переноса Confluence ACL и независимой экспертной оценки датасета.
- Для Python перед каждым вызовом обязателен get_python_environment из python-tools; SDK API/worker — соответствующие .venv, Python 3.12.14. TestClient и Docker/live API требуют разрешённого выхода из sandbox; зависание TestClient при teardown воспроизводится в terminal sandbox и не является доказанной ошибкой endpoint-ов.
