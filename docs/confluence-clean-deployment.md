# Чистое развёртывание RAG для Confluence

Профиль `deploy/docker-compose.clean.yml` устанавливает собственный экземпляр
без прежних рабочих областей, баз знаний, документов, диалогов и демонстрационных
архивов. Содержимое Confluence импортируется только после выбора пользователем.
Профиль предназначен для команды с общей областью доступа к документам.

## Что входит в установку

Шесть сервисов: PostgreSQL с pgvector, Redis, MinIO, API, worker и web.
Доступ к Confluence идёт напрямую из API: `CONFLUENCE_CONNECTION_MODE=direct`,
`CONFLUENCE_CONNECTOR_ENABLED=false`. Отдельный connector нужен для сетевой
изоляции; в этот профиль он не входит. Машина Docker должна иметь сетевой
доступ к Confluence и двум внешним API моделей.

LLM, embeddings и GPU в профиль не входят. LLM должен поддерживать
OpenAI-совместимый `POST /v1/chat/completions`. Текущий клиент embeddings
использует **другой протокол**: `POST /embed`, тело
`{"inputs":["текст"],"normalize":true,"truncate":true,"input_type":"query"}`
для поиска и `input_type=passage` для документов. Ответ — массив векторов.
API `/v1/embeddings` без адаптера не подходит. Авторизация embeddings-клиентом
сейчас не передаётся: нужен доступный в доверенной сети endpoint или шлюз.
`EMBEDDING_DIM` должен совпадать с размерностью векторов; допустимо 1–2000.
Модель должна быть одна и та же для индексации и поиска. Reranker отключён.
Docling и скачивание его моделей отсутствуют в лёгком worker.
Загруженные PDF обрабатывает PDFium, сканы — Tesseract. Импорт страницы Confluence охватывает её текст и структуру; вложения можно загрузить как отдельные документы. Он предназначен прежде
всего для текстового содержимого выбранных страниц Confluence.

### Объектное хранилище в локальном пилоте

Community-репозиторий MinIO [архивирован владельцем 25 апреля 2026 года](https://github.com/minio/minio)
и переведён на распространение исходников. Поэтому чистый профиль собирает
собственный образ из официального commit
`7aac2a2c5b7c882e68c1ce017d8256be2feea27f` от 12 февраля 2026 года.
Перед компиляцией проверяется SHA-256 исходного tar.gz:
`71794c2df26aad0cc99e8421c58b7aa2dd55969f979b0e7d1e931042e9fabcd6`.
Dockerfile лежит в `apps/object_store/Dockerfile.clean`; Go и Alpine
закреплены по digest. Сторонние готовые образы MinIO не используются.

Первоначальная сборка требует загрузки Go-зависимостей и компиляции; итоговый
контейнер содержит бинарный файл, CA certificates, LICENSE/NOTICE/CREDITS
и запускается пользователем `10001`, без root. Новому именованному volume
передаются права каталога `/data` из образа. Старый volume этим профилем не
подключается и автоматически не изменяется.

Этот архивированный сервер оставлен для локальной проверки существующего
S3-контракта приложения. Перед промышленной эксплуатацией следует выбрать
поддерживаемое S3-совместимое хранилище, проверить SDK-совместимость,
права доступа и перенос объектов. Сборка старых исходников сама по себе
не обеспечивает дальнейших исправлений безопасности.

## Подготовка локального экземпляра

Нужны Python 3 и Docker с Compose v2. Команды выполняются из корня распакованных
исходников. Скрипты используют локальный Unix-сокет Docker или Docker Desktop;
удалённые Docker-контексты отклоняются. Работающий удалённый RAG эти команды
не изменяют.

```bash
./scripts/deploy/setup-clean-env.sh --output ./confluence-clean.env --mode pilot
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env build
```

Первая команда создаёт новый файл с правами `600`, случайными паролями сервисов
и уникальным именем проекта `rag-clean-*`. Существующие файлы не перезаписываются;
обычный `.env` не используется. Для каждого нового независимого экземпляра
сгенерируйте свой файл. Не копируйте имя проекта от прежней установки.

Сборка возможна до получения внешних доступов. Для запуска заполните созданный
файл в локальном редакторе:

| Настройки | Назначение |
| --- | --- |
| `VLLM_BASE_URL`, `VLLM_MODEL`, при необходимости `VLLM_API_KEY` | Внешняя модель ответов; base URL может заканчиваться на `/v1` |
| `EMBEDDING_BASE_URL`, `EMBEDDING_MODEL`, `EMBEDDING_DIM` | Endpoint протокола `/embed`, обозначение модели и размерность |
| `CONFLUENCE_BASE_URL`, `CONFLUENCE_DEPLOYMENT` | HTTPS-адрес и `cloud` либо `data_center`; Cloud `/wiki` обрабатывается клиентом |
| `CONFLUENCE_AUTH_MODE` | `basic` или `bearer` |
| `CONFLUENCE_EMAIL`, `CONFLUENCE_API_TOKEN` | Серверная учётная запись для `basic` |
| `CONFLUENCE_ACCESS_TOKEN` | Серверный токен для `bearer` |
| `CONFLUENCE_ALLOWED_SPACES` | Явный список ключей разрешённых пространств через запятую, например `DOCS,OPS` |

Не указывайте токены в URL. Файл содержит литеральные значения `KEY=value`:
без кавычек, shell-подстановок и `$`. В Linux-контейнере `localhost` означает
сам контейнер. Для сервисов на хосте используйте доступный контейнерам адрес,
например настроенный `host.docker.internal` в Docker Desktop. HTTPS-сертификаты
должны быть доверены контейнерами; проверка сертификатов Confluence включена.

```bash
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env config
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env --allow-local-pilot up
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env ps
```

`config` проверяет полноту настроек и структуру Compose, не печатает секреты
и не проверяет доступность удалённых сервисов. `up` дополнительно требует
явного `--allow-local-pilot` для режима без входа. Web слушает только
`http://127.0.0.1:18573`; остальные порты на хост не публикуются. При смене
`RAG_WEB_HOST_PORT` обновите также `WEB_ORIGIN` на соответствующий loopback URL.

После запуска откройте web, создайте рабочую область, выберите доступные
пространства и страницы Confluence, запустите импорт и дождитесь индексации.
Затем проверьте вопросы с известным ответом и переходы к источникам. Пустая
установка сама не создаёт пространства Confluence и не импортирует весь wiki.

```bash
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env logs
./scripts/deploy/compose-clean.sh --env-file ./confluence-clean.env down
```

`down` останавливает только выделенный проект и сохраняет его данные; флага
удаления volumes в wrapper нет. `build`, `down`, `ps`, `logs` работают и при
ещё незаполненных внешних настройках. Логи могут содержать сведения об
импортируемых документах — проверяйте их перед передачей другим людям.

## Общая установка с входом

Для общего сервера создайте отдельный файл через `--mode oidc` и задайте
`OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `OIDC_CLIENT_ID`,
`OIDC_REDIRECT_URI`, `OIDC_POST_LOGOUT_REDIRECT_URI`, `WEB_ORIGIN`.
Внешние адреса OIDC и web должны быть HTTPS; алгоритм подписи — асимметричный.
Зарегистрируйте frontend как публичный OIDC-клиент с PKCE и разрешёнными
redirect URI. По умолчанию API ожидает claims `tenant_id`, `roles`; согласуйте
их с провайдером и выдайте администраторам роль `rag-admin`.

Внешний HTTPS reverse proxy должен обращаться к loopback-порту web. Сам
профиль не устанавливает провайдер входа, proxy или сертификаты. Запускайте
через `compose-clean.sh --env-file ./confluence-oidc.env up`.

**Граница доступа:** прямое подключение читает Confluence от одной серверной
учётной записи и общего allowlist. Это не перенос персональных прав каждого
пользователя Confluence. Доступ к полученным документам определяется RAG.
Объединяйте только материалы, которые разрешено видеть всей целевой команде;
для пользователей с разными правами нужны отдельные установки/области доверия
либо отдельная реализация проверки ACL источника. OIDC сам по себе эту задачу
не решает.

Инициализация выполняет миграции и согласует размерность векторного столбца
только при пустой таблице. Изменение модели или размерности после загрузки
документов требует отдельной миграции и переиндексации; обычный рестарт для
этого не предназначен. До промышленного выпуска необходимо закрепить digest
базовых образов, настроить резервное копирование, мониторинг и проверить
реальные интеграции и права доступа.

## Передача чистых исходников

```bash
./scripts/deploy/package-clean.sh --output /tmp/rag-confluence-clean-source.tar.gz
cd /tmp
sha256sum --check rag-confluence-clean-source.tar.gz.sha256
```

Это архив исходников для сборки, а не готовый контейнерный релиз. Allowlist
включает код API/worker/web, миграции, чистые Dockerfile (в том числе сборку
объектного хранилища), Compose, шаблон
настроек, эту инструкцию и скрипты. Прежние `.env`, volumes, `.storage`,
snapshots, корпуса оценивания, презентации, публичные demo-архивы,
`node_modules`, virtualenv и логи не включаются.
Внутри `CLEAN_SOURCE_MANIFEST.json` перечислены включённые файлы и их SHA-256;
рядом с архивом создаётся `.sha256`. После распаковки снова выполните `setup`
для получения собственных секретов.

Проверка защитных контрактов упаковки и wrapper без сети и Docker:

```bash
python3 -m unittest discover -s tests -p test_clean_profile.py -v
```
