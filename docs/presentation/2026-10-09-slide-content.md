# Слайды: «Корпоративные знания — от статьи к проверяемому ответу»

Дата выступления: 9 октября 2026 года. Формат: 22 минуты основного показа
и до 3 минут вопросов. Всего 5 слайдов; большую часть времени открыт продукт.
Полный текст и действия — в [сценарии](2026-10-09-speaker-script.md).

Ниже текст, который действительно должен находиться на слайдах. Пояснения
после «Заметки» — только ведущему, не текст для проектора.

## Слайд 1. Знания должны работать

**Быстрее подготовить документ. Быстрее найти проверяемый ответ.**

Техписатель → понятная инструкция и проверенные правки.

Инженер → ответ, полный исходный код и ссылка на оригинал.

Confluence AI Reviewer · Корпоративный RAG

**Два проекта. Один рабочий процесс. Решение остаётся у человека.**

### Заметки

Время: 0:00–1:30. Не начинать с моделей, фреймворков и перечня технологий.
Начать с двух рабочих задач: техписателю быстрее подготовить понятную
инструкцию, инженеру быстрее найти подходящий документ и точный ответ.
Упомянуть уже подключённый Just AI: пользовательский опыт пока не удовлетворяет,
но корпус для него ещё не подготовлен. Это исходная ситуация, не сравнительный
benchmark и не доказательство плохого качества платформы. Обещание выступления:
подготовленные реальные статьи, воспроизводимый технический текст и оригинальный URL.
Интеграция Reviewer с RAG пока не реализована; слайд связывает задачи,
а не утверждает наличие общего backend или автоматического обмена результатами.

## Слайд 2. Два управляемых контура

**Автор**

Черновик Confluence → проверка → предложение → Apply / Undo

**Инженер**

Confluence → connector → база знаний → поиск → ответ + источники

Модель предлагает. Приложение проверяет контракт. Человек принимает решение.

### Заметки

Время: 1:30–2:15, затем переключиться в Confluence и запустить Reviewer.
Во время ожидания показать RAG: живой connector, дерево доступных пространств,
готовые тематические KB и workspace. Модель Reviewer анализирует настоящий
несохранённый черновик; локальная точечная правка не заменяет всю страницу.
Apply меняет черновик; сохранение и публикация выполняются механизмами
Confluence, а не автоматически моделью. Перед демонстрацией ничего не
публиковать и не выполнять shell-команды.

8 октября проверен текущий несохранённый черновик: 72 363 мс, пять замечаний.
Проверенная карточка `systmctl` → `systemctl` меняет только первое вхождение;
три таблицы и два макроса остаются, native Ctrl+Z точно восстанавливает HTML.
Это proof конкретного workflow, не метрика качества всех пяти замечаний.
В live называть кнопку «Применить»; для Undo использовать Ctrl+Z с фокусом
в редакторе. Предупреждения Confluence заранее закрыть временным Close.
Затем в новой изолированной сессии проверен весь workflow через внутренний
`https://192.0.2.122:15174/confluence`: review 59 084 мс, точечная правка,
точное восстановление HTML native Ctrl+Z и неизменённая опубликованная v1.
Это два конкретных прогона, не p95/SLA. На сцене говорить «около минуты».
Основной браузерный URL — серверный HTTPS даже на ноутбуке; loopback `:23990`
остаётся backend upstream. Отдельный gateway-пароль и штатный Confluence login.

Connector использует права подключённой учётной записи. Он не обходит
Confluence permissions. Демонстрационный RAG без авторизации не зеркалирует
ACL разных пользователей — этот важный предел проговорить в финале.

## Слайд 3. Вопрос — не всегда набор ключевых слов

**Смысл** — BGE-M3, dense 1024

**Точное имя** — лексический поиск PostgreSQL

**Вместе** — hybrid / RRF

`ostor-agentd.env`: покажем три настоящие выдачи рядом.

Генерация: корпоративная Qwen3.8 · reranker в этом стенде отключён.

### Заметки

Время: 8:30–9:00, затем UI «Разбор поиска». Три канала поиска показывают
разные механизмы попадания фрагмента в выдачу, а не три варианта генерации.
Hybrid объединяет ранги; это не новый фундаментальный алгоритм и не
утверждение об универсальном превосходстве. BGE-M3 здесь используется только
для dense embeddings, не для native sparse или ColBERT. Не интерпретировать
score как вероятность правильности и не называть показанный пример benchmark.
Фактическая модель генерации — Qwen/Qwen3.8-27B-FP8 за alias corporate-llm.

## Слайд 4. Для команд нужна проверка, а не только ссылка

Ответ → фрагмент источника → страница и версия → дословный полный блок

**Детерминированная проверка вне LLM**

Полный блок · оригинальный URL и версия · SHA-256

**Дословно ≠ безопасно или применимо. Нет основания → отказ.**

### Заметки

Время: 14:30–14:55, затем показать ответ на реальный вопрос о службах Ostor.
Проверка сопоставляет полный fenced-блок ответа с полным блоком в контексте,
который действительно передавался модели. Нормализация ограничена CRLF и
разделительным завершающим переводом строки у fence. Это не анализатор shell,
не проверка технической истинности и не электронная подпись. SHA-256 —
идентификатор проверяемого текста, не доказательство актуальности источника.

Наличие страницы и версии показывает происхождение; ссылка обычно открывает
текущий оригинал Confluence, поэтому версия при импорте может отличаться.
Номер цитаты или имя локального файла не заменяет оригинальный URL. Полный
code block не равен полной процедуре: предусловия и остальные шаги могут
оставаться в соседних разделах. В обработке сохраняем fenced-блоки целиком;
подрезанный контекст нельзя компенсировать выдуманными параметрами.
Для явного запроса полного дословного кода неподтверждённая дословность
останавливает ответ. Не обещать такой fail-closed для любого вопроса о командах.
Inline-команды вне fenced-блоков этим аудитом не проверяются.

## Слайд 5. Следующий шаг — измеримый пилот

**Уже можно показать**

Реальные статьи · прозрачный поиск · источники · локальные правки · контроль кода

**Перед production**

Права каждого пользователя · актуальность · независимая оценка качества

**Внутренний RAG:** источники · индекс · корпоративная модель

**Пилот:** время техписателя и инженера + качество ответов и правок

### Заметки

Время: 18:45–22:00. Не объявлять проекты production-ready и не выдавать
успешные HTTP-запросы или зелёные unit-тесты за точность модели. Измерять
retrieval отдельно от корректности итогового ответа; у Reviewer — принятые,
отклонённые и действительно полезные замечания, а не число созданных карточек.

Реальные результаты подготовки: 309 текущих страниц READY, три KB по четыре
страницы, девять сохранённых ответов сверены вручную с источниками, 4/4 полных
блоков в подготовленном ответе команд, 0/1 подтверждённых якорей для отсутствующего
идентификатора и отказ. 166 выбранных API-тестов проходят. Это подтверждение
готовности конкретных механизмов и демонстрационного набора, не 100% точность
на произвольных запросах и не сравнительные метрики Just AI.

Expected-page Hit@5 — 8/8 в каждом из dense / lexical / hybrid на восьми
отрепетированных положительных вопросах, по четыре документа в выбранной KB.
27 search-запросов без HTTP-ошибок, без генерации LLM на шаге поиска.
Это демонстрационный acceptance-набор, не независимый benchmark или
доказательство превосходства одного канала.

Для RAG источники, индекс и inference находятся внутри корпоративной сети;
совместимый с OpenAI API не означает отправку документов в OpenAI/SaaS.
Для удалённого Reviewer проверена внутренняя схема: HTTPS на
`192.0.2.122:15174` + обратный SSH-туннель к ноутбуку. Ngrok и внешний
транзитный сервис не используются. В новой изолированной браузерной сессии
подтверждены login, редактор, native review, точечная правка и Undo через серверный URL.
Приложение не мигрировано: ноутбук должен оставаться включённым. До проектора
проверить SHA-256 отпечаток самоподписанного сертификата и настроить доверие.
Это временный внутренний proxy, а не объявление production-security.
Локальный clone содержит также два пространства вне QAEVAL: он не исключительно
синтетический; требования к допустимым данным и авторизации остаются.

У Reviewer остаются semantic defects; текущий изменённый working tree
не объявлен целиком зелёным. В замороженной сборке v8 проверены workflow и
обработка конкретных отказов, но независимая финальная оценка не завершена.
Для RAG нужны ACL на уровне retrieved context, а не скрытие ссылки в UI,
а также auth/TLS/service authentication и согласованный набор разрешённых данных.

Возможная общая карточка Reviewer + RAG — направление развития, не готовая
интеграция: замечание → цитата руководства → версия → условия применимости.
Следующий этап для схем и фото — OCR/vision с оригинальным источником и
отдельными тестами. Сейчас изображения помечаются `images_not_recognized`,
а нетекстовый draw.io — `unresolved_macro:drawio`; storage XHTML не включает
получение вложенных бинарных изображений. На S3-странице `189231226`, v18
наблюдалась такая заглушка. Ответ по соседнему тексту не означает понимания схемы.
Just AI уже подключён; сообщённая пользователем неудовлетворённость текущим
результатом при неподготовленном корпусе — контекст задачи. Сравнительные
проценты не придумывать; предложить измерение на одинаковом подготовленном корпусе.

## Что не выносить на слайды

- Секреты, PAT, enrollment token, `.env`, raw reasoning модели.
- Неподтверждённые проценты улучшения качества, рыночную уникальность или
  обещания «без галлюцинаций».
- Длинные листинги кода и таблицы всех внутренних компонентов: это лучше
  показать в интерфейсе на одном понятном примере.
- Старые числа документов как актуальный охват живого connector.
- Just AI как «плохое решение» без одинаковых исходных условий измерения.
- Фотографии и схемы как уже работающую multimodal-возможность без проверки.

## Короткие подписи для визуальной сборки

1. **Создаём знания. Используем знания.**
2. **Контроль встроен в рабочий процесс.**
3. **Ищем по смыслу и точным именам.**
4. **Проверяем то, что можно проверить точно.**
5. **Расширяем пилот по измерениям, не по впечатлению.**
