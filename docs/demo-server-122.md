## Модели и границы стенда

- Генерация: существующий корпоративный OpenAI-compatible сервер
  `http://192.0.2.122:18437`, model alias `corporate-llm`,
  фактическая модель `Qwen/Qwen3.8-27B-FP8`.
- Поиск: отдельный GPU-сервис `BAAI/bge-m3`, dense vectors 1024, FP16.
  Лексический поиск — PostgreSQL; hybrid объединяет каналы. Это не
  использование sparse/ColBERT выходов BGE-M3. Reranker отключён.
- Общий LLM и чужие контейнеры не изменяются. Внутренние БД, Redis,
  MinIO и embedding не публикуют порты на хосте.
- Это стенд без авторизации, привязанный к указанному внутреннему IP.
  Он не предназначен для открытого Интернета и не зеркалирует Confluence ACL.
- Worker собран без Docling: демонстрация Confluence/Markdown, не PDF OCR.

## Управление

Выполнять из каталога стенда с правами на Docker:

```bash
# Первый запуск или восстановление конфигурации на этом сервере.
bash scripts/deploy/start-demo.sh

# Проверка и логи.
bash scripts/deploy/compose-demo.sh ps
bash scripts/deploy/compose-demo.sh logs --tail 100 api worker embedding

# Обычный повторный запуск; данные сохраняются в именованных volumes.
bash scripts/deploy/compose-demo.sh up -d

# После пересоздания API проверить его health и перезапустить web:
# Nginx разрешает адрес upstream при старте.
docker inspect rag-zmostovoy-api-1 --format '{{.State.Health.Status}}'
bash scripts/deploy/compose-demo.sh restart web

# Остановка только этого проекта, без удаления данных.
bash scripts/deploy/compose-demo.sh stop
```

`.env.demo` создаётся с правами 0600 и случайными паролями БД/MinIO.
Не публиковать этот файл и не включать его в демонстрационные материалы.
`setup-demo-env.sh` сохраняет существующий файл. Для первого старта требуется
загрузка весов BGE-M3 из Hugging Face; healthcheck допускает длительный старт.
Базовый CUDA-образ переиспользует уже имеющийся `vllm/vllm-openai:v0.30.0`;
его исходный LLM entrypoint заменён, запускается только embedding API.

## Живой connector на ноутбуке

Коннектор работает как пользовательский сервис `rag-confluence-122.service`
на ноутбуке Zakhar. Пока ноутбук включён, пользовательский сервис работает
и доступны корпоративная сеть/VPN и Confluence, новые списки и импорты
обслуживаются автоматически. Выключение или сон ноутбука останавливают
живой доступ, но не поиск по уже готовым индексам сервера.

Проверять на ноутбуке до выступления, не показывая секреты на проекторе:

```bash
systemctl --user is-active rag-confluence-122.service
systemctl --user status rag-confluence-122.service --no-pager
```

В RAG открыть workspace «00 · Confluence · живой KBR» → Confluence:
статус online, «Показать пространства»/«Обновить», поиск `KBR` и раскрытие
дерева. Online означает связь connector с RAG; успешный список и чтение
страницы дополнительно подтверждают доступ к Confluence.

Используется явный `--all-accessible-spaces`: фактические доступные ключи,
без wildcard и без обхода Confluence ACL. Личные пространства скрыты в
первоначальном интерфейсе, но доступны через поиск или явную кнопку.
Секреты Confluence остаются локально. Машинный credential автоматически
отдельный для каждого RAG URL; старый credential не перезаписан.
RAG-пилот без авторизации не переносит индивидуальные ACL в готовый индекс.

## Что показывать

1. Живое подключение Confluence и три тематические опубликованные KB.
2. «Разбор поиска»: один вопрос → dense / lexical / hybrid, реальные позиции,
   совпавшие фрагменты, версии и ссылки. Числа score не являются вероятностью
   правильного ответа.
3. Реальный вопрос о полных блоках команд Ostor: источник, версия, аудит дословности.
4. Невстречающийся идентификатор: показать отказ вместо выдуманной инструкции.

DEMO-TS-742 и DEMO-TS-743 остаются отдельным учебным резервом; основной
показ теперь построен на реальных статьях, а не синтетических примерах.

Для корпоративного KBR проверен вопрос: «Какими командами проверить состояние
служб Ostor? Приведи полные исходные блоки дословно, не объединяй разные блоки».
В сохранённом чате тематической KB подтверждены 4 из 4 полных блоков с
Confluence page/version witnesses. В первоначальном контрольном прогоне
старого корпуса были 6 из 6; число блоков зависит от переданного контекста.
Это проверка дословности, не утверждение, что все
выданные диагностические команды применимы к конкретному рабочему узлу.

Проверка кода детерминированно сопоставляет полные fenced-блоки ответа с
фрагментами, переданными модели. Допускается нормализация CRLF и завершающего
перевода строки у fence; остальной текст и порядок строк внутри блока
должны совпадать. Это не доказательство безопасности команд, применимости
к текущей системе, полноты инструкции или порядка между отдельными блоками.
Статус `no_code` не означает подтверждённый ответ. Команды из демонстрации
не выполняются. Извлечение источников и генерация по-прежнему могут ошибаться;
стенд не заменяет качественную оценку на размеченном наборе.

Сравнение с Just AI добавлять только при наличии сопоставимых запросов,
корпуса и результатов измерения. Старые HTTP-успешные прогоны не следует
называть доказательством улучшения качества.
